# gangU - Key Architectural Decisions

Tracking issue: #39. Grounded in main @ `1c0c8a3deadd3282ae19b82c7e3cc9f640c73b77`.
Each entry states the decision, where it lives in code, and why. Status is one of:

- **Implemented** - merged and verifiable in the current source.
- **Provisional** - merged as a labeled harness default, explicitly not settled.
- **Open** - a human choice; no code may presume an answer.

---

## Implemented decisions

### D1. Platform and stack
Godot **4.5.1-stable** (pinned exactly) + GDScript. Web/HTML5 is a first-class target: renderer `gl_compatibility` (broad WebGL2 support) and thread support OFF so the build runs on plain static hosting without COOP/COEP headers.
*Where:* `project.godot`, `export_presets.cfg`, README.

### D2. Display contract
Viewport 1152x648, stretch mode `canvas_items`, aspect `expand`. Working convention: layout claims get checked at multiple window sizes before merge; #50 tracks a known cosmetic overlap that remains open under it.
*Where:* `project.godot`.

### D3. Input: shared project-level actions, manual aim only
`move_up/down/left/right` (WASD) and `cast` (Space + left mouse button) are defined once in `project.godot` and consumed everywhere; no scene redefines them. Manual aim only, no aim assist; keyboard + mouse, trackpad-friendly. `switch_spell` exists as an action with **no key bound** (open choice, see O2).
*Where:* `project.godot`, `scripts/player.gd`, `scripts/spell_caster.gd`.

### D4. One Main scene; systems are code-mounted, not scene-edited
`scenes/main.tscn` stays minimal (Player + FollowCamera). `main.gd._ready()` mounts BackgroundGrid, RunManager, HUD and ReviveSatchel in code; `_swap()` mounts per-area content (demo enemies, objective, exit portal). This keeps shared scene files out of merge contention and keeps mount ordering explicit.
*Where:* `scripts/main.gd`.

### D5. The shared Player is never recreated during a run
Area swaps (hub <-> dungeon) reposition the existing Player at the area's `PlayerSpawn` marker; HP, spells and carried items persist across travel for free. The only reset is the RunManager's full scene reload on death. Transport is deferred (`call_deferred`) because it starts inside physics callbacks.
*Where:* `scripts/main.gd` (`_swap`, `_on_gate_entered`, `_on_exit_portal_entered`).

### D6. Explicit wiring beats group lookups in production
The production Player is in **no group**. Cross-node references are exported NodePaths (`player_path`, `objective_path`) set **before** the node enters the tree, resolved in `_ready`. Group lookup remains only as a fallback so older test fixtures keep working; ReviveSatchel has no fallback at all (accepted #6/#12 contract - a missing `player_path` is an error, not a silent idle).
*Where:* `scripts/main.gd`, `scripts/hud.gd`, `scripts/enemy.gd`, `scripts/run_manager.gd`, `scripts/revive_satchel.gd`; gap history in #34.

### D7. Single HP mutation entry points
`Player.apply_damage()` / `Player.heal()` and `Enemy.apply_damage()` are the only places HP changes. Each clamps and emits `health_changed` from inside, so HP can never change silently; `died()` fires exactly once at HP 0. `heal()` works from HP 0 (the revive path); the HUD recovers via `health_changed`.
*Where:* `scripts/player.gd`, `scripts/enemy.gd`.

### D8. Spells are data; the caster owns collection, cooldowns and switching
All spell stats live on `Spell` resources (`resources/spells/*.tres`), never hardcoded in casting logic. `SpellCaster` owns the collected spell array, per-spell cooldowns keyed by the Spell object, the equip index, and switching (`add_spell` / `next_spell`). Switching was added in the caster so `player.gd` stayed untouched (#10 stage 1).
*Where:* `scripts/spell.gd`, `scripts/spell_caster.gd`.

### D9. Systems talk through signals, not reach-ins
The published contracts: `Player.health_changed/died`, `SpellCaster.spell_cast/cooldown_started/spell_equipped/spell_added`, `Enemy.died/health_changed`, `DungeonObjective.objective_progress_changed/objective_completed`, `Gate.entered`, `ExitPortal.entered`, `ReviveSatchel.revive_collected/revive_used`, `RunManager.run_restarting`. Consumers connect; producers never know their listeners.
**On-hit (#390):** every DamageCalc call site (projectile, Stone Hammer slam/shockwave, Water Splash/Bubble, summon guard melee, enemy chase/contact) reports each landed hit on the one shared `OnHit.bus().hit_landed(HitEvent)` signal. Call sites wrap the apply call in `OnHit.begin(target)` / `OnHit.end(receipt, target)`; production receivers (Player, Enemy, Summon, DestroyableContainer, DefenseCore) call `OnHit.record(self, hp_before, hp_after)` at their HP mutation point, before `health_changed`/`died`. **Landed = the receiver accepted it:** a receiver that returns early (Player invulnerability, already dead, a container refusing a non-Player source) records nothing and no event is emitted; an accepted 0-damage hit still lands with `hp_lost` 0. Payload: `attacker` (null when none or freed - a shot can outlive its shooter; arguments are untyped and normalized so a freed source is never a script error), `spell` (null for contact), `target`, `result` (the DamageCalc **roll**, not HP lost), `hp_lost` (HP actually removed), `killed` (THIS hit took hp to 0, captured at the receiver so a synchronous revive or a later follow-up hit cannot change it), `delivery` (`OnHit.DELIVERY_*`), `position`. On-hit effects connect there and filter in the handler instead of being wired per spell/receiver. Foundation only: no existing bespoke wiring (damage numbers, Hammer Reaper, relic passives) is migrated, no effect content exists, it stands alone from `DungeonModifierHost` (#222), and hits that bypass DamageCalc (boss lunge/pulse/spin/scream) do not report. `scripts/test390_on_hit.gd` pins it.
*Where:* the scripts above; `scripts/on_hit.gd`, `scripts/hit_event.gd`.

### D10. Death means a full run restart; revive intercepts synchronously
On `died()`, RunManager first offers the satchel a synchronous `try_revive()` **before** latching anything; a carried item cancels the restart entirely (scene survives, upgrades/state persist). Otherwise it disables every caster on the player (`PROCESS_MODE_DISABLED`, so a dead player can never cast during the pause) and reloads the whole scene after a short delay - HP, enemies, projectiles and pickups all rebuild from the scene definition. The satchel deliberately has **no** `died()` listener: interception ordering is owned by the run manager, never by signal order.
**Reset scope (#351, Colin 2026-11-08):** death is a FULL reset - world (back to the hub, enemies/pickups respawn), dungeon cleared-state, spells, upgrades, coins and the map. No partial carryover. Run state that lives outside the reloaded scene (autoloads, root-parked nodes - e.g. overworld cleared-state #348, the map #347) must join the `run_state` group (`RunManager.RUN_STATE_GROUP`) and implement `reset_run_state()`; RunManager calls it right before the reload. Cross-run meta records (Bestiary #325) are not run state. `scripts/test351_full_reset.gd` pins this.
*Where:* `scripts/run_manager.gd`, `scripts/revive_satchel.gd`.

### D11. Objectives are data-driven, one node per dungeon, mounted after enemies
`DungeonObjective` supports `CLEAR_ALL_ENEMIES` (target 0 = every enemy present at ready) and `DEFEAT_BOSS`. Its `_ready` scans the `enemies` group, so `main.gd` mounts it **after** the area's enemies or the target computes as 0 and never completes. Production DungeonA runs CLEAR_ALL over the demo enemies; DungeonB runs ELIMINATION (mobs, then the Mustache Warlord; O1, 2026-11-08); DungeonC runs ELIMINATION with zero mobs, so the Head boss spawns on entry (O6, 2026-11-08); DungeonD does the same for the Beast boss (O7, 2026-11-09). DungeonE runs DEFENSE (#337, O10): protect the area's `DefenseCore` through a fixed number of periodic waves that the objective spawns itself (through an EnemySpawner); completion = every wave cleared, and a destroyed core emits `objective_failed` instead. Completion emits `objective_completed(dungeon_id)`.
*Where:* `scripts/dungeon_objective.gd`, `scripts/main.gd` (`_mount_objective`).

### D12. Exit portals: retreat-anytime on normal, clear-or-die on red
Normal-gate dungeons mount the portal **unlocked** (objective not required). Red-gate dungeons and the boss-gate arenas (DungeonC, O6; DungeonD, O7) mount it **locked**. "Red" means the type of the gate actually entered (#350, since offerings roll by chance), falling back to DungeonB when an area is mounted without a gate. DungeonE (DEFENSE, #337) is entered through a NORMAL gate, so its portal is unlocked; if it is ever mounted locked, a failed defense (`objective_failed`) unlocks it so the run cannot soft-lock. A locked portal opens on `objective_completed` via a duck-typed `objective_path` (signal-name check, so the portal file stands alone). Using a portal returns to the hub in the same run (see D5); the dungeon entrances themselves are in the overworld (D21).
*Where:* `scripts/exit_portal.gd`, `scripts/main.gd` (`_mount_exit_portal`).

### D13. Gates are typed transport only
`Gate` carries `gate_type` (NORMAL/RED/BOSS/TRAVEL - BOSS is the violet gate type used by GateBoss -> DungeonC, O6, and GateBeast -> DungeonD, O7; TRAVEL is the gold hub <-> overworld passage, D21), tint and label, and emits `entered`; it owns no lock-in rules. Travel gates name their target by `target_path` (the hub and overworld point at each other, so PackedScene references would be a cyclic load). Labels sit inside the gate rect and clear of the HUD (#44). Since #350 (Colin, 2026-11-08), there is **no rank system**: whether a dungeon offering is NORMAL or RED is decided by chance, 50/50. A gate with an `offering` (`GateOffering`) rolls its type once per run and Main caches the roll per gate, so the type stays fixed until death; the death restart reloads Main and clears the record. BOSS gates never roll. The overworld's GateNormal and GateRed share `resources/gate_offering.tres`. GateGenerated is not an offering because its dungeon has no objective, so a RED roll could never lock in.
*Where:* `scripts/gate.gd`, `scripts/gate_offering.gd`, `scripts/main.gd` (`offering_type_for`), `resources/gate_offering.tres`, `scenes/overworld.tscn`.

### D14. Never mutate the tree synchronously inside physics callbacks
Scene swaps, pickup consumption and portal returns use `call_deferred` / `set_deferred` - nothing is freed or swapped inside `body_entered`.
*Where:* `scripts/main.gd`, `scripts/spell_pickup.gd`, `scripts/exit_portal.gd`.

### D15. Camera: smoothed follow on physics ticks
The follow camera lerps toward the player with frame-rate-independent exponential smoothing, in `_physics_process` (not `_process`): the player moves on fixed physics ticks, and sampling that step-wise target on render frames caused visible jitter (#29). It snaps only on ready so the first frame is framed correctly. It lives in `main.tscn`, independent of player.tscn changes.
*Where:* `scripts/camera_follow.gd`.

### D16. HUD is self-contained and discovers the objective lazily
The HUD (CanvasLayer) connects to explicit player/caster signals, renders nothing it cannot source (the objective row stays hidden where no objective exists), and finds the area-mounted `DungeonObjective` by throttled lazy search, using `is_instance_valid` (a freed objective does not compare == null). Its 3x2 spell grid polls the six equip slots every frame, so an unequipped pickup does not appear (#238).
*Where:* `scripts/hud.gd`.

### D17. Demo content scope is human-approved config, code-mounted
DungeonA (normal gate) carries exactly three enemies, spread away from the entrance spawn - the approved demo configuration, declared as constants in `main.gd`, not invented defaults. #392 (Daniel, 2026-11-09: "spawn them in a dungeon, and near that dungeon's gate in the overworld", then "sure" to DungeonA added alongside) adds two splitting Slimes to DungeonA's SpawnData (so five enemies at ready; each 80 HP slime leaves 2 + 4 descendants, and the CLEAR_ALL objective counts them through `EnemySlime.children_spawned`) and one slime gate guard to the overworld's GuardsNormal. Slime stats are PLACEHOLDER; splitting needs max HP >= 40. DungeonB (red gate) carries three mobs plus the Mustache Warlord boss via ELIMINATION (human decision 2026-11-08, see O1). DungeonC (boss gate) is a boss arena only: the Head boss, no mobs (human decision 2026-11-08, see O6). DungeonD (BOSS-type gate labelled BEAST) is the Beast boss's arena, no mobs (human request 2026-11-09, see O7). DungeonE (NORMAL gate labelled DEFENSE) is the defense mission: no SpawnData, its waves come from the DEFENSE objective (#337, see O10).
*Where:* `scripts/main.gd` (`DEMO_ENEMY_POSITIONS`, `_mount_demo_enemies`).

### D18. Projectiles duplicate their collision shape per instance
`Projectile._ready` duplicates the collision shape before setting the spell's radius, so per-spell radii never leak across instances sharing the scene. Projectiles despawn at max range, never hit their source, and damage anything implementing `apply_damage`.
*Where:* `scripts/projectile.gd`.

### D19. Evidence standard for gameplay PRs
Mechanics land with headless SceneTree harness drivers plus, for player-visible claims, a browser recording of the exact pushed head with zero console errors, made with real input (synthetic `apply_damage` calls are a named headless complement only). Fixture scenes are labeled evidence fixtures, never described as production.
*Where:* `scripts/test*.gd`, `scenes/test*.tscn`.

### D20. CI/CD: one workflow, PRs build, only main deploys
A single GitHub Actions workflow exports the web build in a pinned `barichello/godot-ci:4.5.1` container. Pull requests get build-only checks; deployment to GitHub Pages happens only on real main-branch pushes. The concurrency group is scoped per ref (`pages-${{ github.ref }}`, cancel-in-progress off) so PR activity cannot cancel a pending main deploy (#52).
*Where:* `.github/workflows/deploy.yml`.

### D21. Overworld between the hub and the dungeons (#346)
Core loop confirmed by Colin (2026-11-08): the hub sits OUTSIDE the overworld and keeps its services (shop, spell directory, bestiary); its single TRAVEL gate (`GateOverworld`) leads to `scenes/overworld.tscn`, which holds every dungeon entrance (GateNormal, GateRed, GateGenerated, GateBoss, GateBeast - #326 integrated in the rebase - and GateDefense, #337) and a TRAVEL gate (`GateHub`) back. Dungeons stay generated/walkable as before. Enemies spawn around entrances whose dungeon is uncleared this run: each entrance has an `EntranceGuards` carrier (AreaSpawnData format + `dungeon_id`), and `main.gd` (`_mount_entrance_guards`) mounts every uncleared set through one EnemySpawner; `cleared_dungeons` is filled from `objective_completed` and resets with the run reload (D10). Guards use `EnemyBehaviorGuard` (leashed chase: hold the post until the player is near or the guard is hit, give up past the leash). #373 (Daniel): overworld enemies move by default - each guarded entrance keeps ONE stationary gate guard and the rest patrol a short closed loop around it (`EnemyBehaviorPatrol`); an overworld-wide `Roamers` carrier (plain AreaSpawnData, no dungeon) holds migrants that travel long open paths, rest at the far end and migrate back (`EnemyBehaviorMigrate`). Both extend the guard and share its aggro/leash (leash measured from where the engagement began; afterwards they resume their route). Routes are an optional `"route"` entry key (area-local points) that `EnemySpawner` hands to the behavior after tree entry. Gate guards and patrols compose with #348 (a cleared entrance loses both); migrants are never suppressed. Route shapes, counts, speeds and rest times are provisional. The overworld floor is code-drawn (`OverworldGround`) from the scene's spawn and gates. Random overworld events, map, fast travel and cleared-entrance behaviour beyond "no guards" are NOT implemented (separate issues / undesigned).
*Where:* `scenes/overworld.tscn`, `scripts/overworld_ground.gd`, `scripts/entrance_guards.gd`, `scripts/enemy_behavior_guard.gd`, `scripts/enemy_behavior_patrol.gd`, `scripts/enemy_behavior_migrate.gd`, `scripts/enemy_spawner.gd`, `scripts/main.gd`.

### D22. Location-triggered events, foundation only (#365)
Requested by Daniel: a reusable way for an overworld location to trigger an event, with ambushes as the example. A `LocationTrigger` (Area2D, group `location_triggers`) is a place authored in a scene: its own CollisionShape2D children set the shape, `trigger_id` names it, and `event` holds an `OverworldEvent` resource. Main wires every trigger in the mounted area (`_mount_location_triggers`). On a fire it bumps the run-scoped history (`location_event_fire_count(id)`, reset by the run reload like `cleared_dungeons`), emits `location_event_triggered(id, trigger)` and starts the event deferred (body_entered arrives during the physics flush, D14) with an `OverworldEventContext` (area, trigger, player, host, run fire count, and `spawn(entries)`, which goes through an area-owned `EventSpawner`, the #220 seam). `AmbushEvent` is the example: it spawns its AreaSpawnData-format `entries` (area-local, or offsets from the trigger with `relative_to_trigger`) and emits `ambush_started`. No repeat or reset rule is assumed. By default every Player entry into an armed trigger fires it. Rules go behind `LocationTrigger.should_fire` (the seam), `arm()`/`disarm()`, and the run history. No production scene places a trigger or an ambush yet. Trigger spots and shapes, repeat/reset rules, ambush composition and counts, rewards and "ambush cleared" handling are undesigned and left to later issues. Covered by `test365_location_events`.
*Where:* `scripts/location_trigger.gd`, `scripts/overworld_event.gd`, `scripts/overworld_event_context.gd`, `scripts/ambush_event.gd`, `scripts/main.gd`.
